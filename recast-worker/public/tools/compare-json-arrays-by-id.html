How Recast chooses a matching key

Recast looks for a field that exists and is unique in both arrays, using common identity fields such as id, uuid, _id, key, slug, code and name. If no reliable shared key exists, it falls back to comparing by position instead of silently pairing the wrong records.

Reordering is not a data change

BEFORE
[{"id":1,"status":"new"},
 {"id":2,"status":"paid"}]
AFTER
[{"id":2,"status":"paid"},
 {"id":1,"status":"shipped"}]

The record with ID 2 is unchanged even though it moved. Recast reports only the status change on ID 1.

Before relying on an ID field

  • Use a key that is present in every record on both sides.
  • Make sure values are unique; duplicate keys make matching ambiguous.
  • Use the same value type in both files—42 and "42" are not necessarily the same identity.
  • Remove volatile fields such as request IDs or timestamps before comparing snapshots.
